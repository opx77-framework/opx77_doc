# opx77_doc

Documentation for **OPX//77**, a roleplay framework for
[OPEN//77](https://open2077.net), the multiplayer platform for Cyberpunk 2077.

Published at <https://opx77-framework.github.io/opx77_doc/>.

Since September 2026 the framework is **one resource, `opx_infinity`**, plus the
client library **`opx_lib`**. This site documents both. The pages for the old
`opx77_*` resources are gone; their URLs redirect to the module that replaced
them (see `redirects` in `mkdocs.yml`).

## What is in here

MkDocs Material sources. `docs/` holds the pages, `mkdocs.yml` the
configuration and the navigation — MkDocs has no autogenerated sidebar, so a new
page is invisible until it is listed in `nav:`.

```text
docs/
├── index.md            the router: "you want to… read…"
├── getting-started/    install, configure, troubleshoot
├── guides/             write a module, write a separate resource, convert, contribute
├── how-it-works/       the runtime explained, one short page per idea
├── modules/            one page per module of opx_infinity (index.md lists them)
├── reference/          core OPX.*, core config, runtime events, lib/, opx_lib, error codes
├── migration/          from opx77_* to opx_infinity, release notes
└── stylesheets/        extra.css, on top of the Material theme

scripts/
├── check-api-coverage.sh   fails on a published name the docs do not document
└── dump-surface.lua        boots opx_infinity on its stub host and prints that surface
```

## How the pages are written

- Every page opens with front matter (`title`, a one-sentence `description`)
  and **one plain paragraph**: what it is and when to use it.
- Short, direct sentences. **Tables** for anything a reader looks up.
- Every module page has the same sections, in the same order: summary table,
  Commands, Server contract, Client contract, Events, Page channels,
  Configuration, Refusal codes. A section the module does not have is left out.
- Every published name has an anchor (`{#anchor}` on a heading, or
  `<a id="anchor"></a>` in a table cell); the rule is in
  [Contributing](docs/guides/contributing.md#anchors).
- Nothing is documented that was not read in the code. The code is the source
  of truth, not the framework README.

## Adding a module

1. Write `docs/modules/<id>.md`, copying the layout of an existing module page.
2. Add it under **Modules** in `mkdocs.yml` (alphabetical) and a row in
   `docs/modules/index.md`.
3. Run the two checks below.

## Building locally

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/mkdocs serve      # http://127.0.0.1:8000
.venv/bin/mkdocs build --strict
```

`--strict` turns warnings into errors: a broken internal link or a redirect
pointing at a missing page fails the build. CI builds with it.

## Checking API coverage

The framework lives in other repositories, so the check needs checkouts of
`opx_infinity` and `opx_lib`, and desktop **Lua 5.4** (`lua5.4` or `lua`):

```bash
./scripts/check-api-coverage.sh                      # finds ../opx_infinity or ../../opx_infinity
./scripts/check-api-coverage.sh /path/to/opx_infinity
OPX_INFINITY=/path/to/opx_infinity OPX_LIB_PATH=/path/to/opx_lib ./scripts/check-api-coverage.sh
```

It does not grep the framework. `scripts/dump-surface.lua` boots the real
manifest on the framework's own stub host (`opx_infinity/tests/host.lua`) and
prints every module, contract member, command, alias, network event, module
event, page channel, config key and `OPX.*` function that is actually
registered; `opx_lib`'s functions are read from its source. The check then fails
on any name without its anchor in the right place. With no framework checkout in
reach it prints a note and exits 0, which is what happens on the CI runner.

## Deployment

Pushing to `main` runs `.github/workflows/deploy.yml`: coverage check (a skip on
CI), `mkdocs build --strict`, then GitHub Pages.
